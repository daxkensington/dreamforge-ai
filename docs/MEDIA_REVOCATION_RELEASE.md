# Media revocation release prerequisite

Migration0016 adds an object ownership/revocation registry and database guards that serialize content writes against account deletion. It does not rewrite old data or delete production objects. Deploy the schema before application code; preserve migrations0000–0015 and the financial ledger. Account deletion scrubs owned projects and their collaboration data, audio, public profile/content, generation prompts and replay results in one transaction. Revocation denies subsequent `/img` origin reads before object deletion. Failed external deletes remain queued and retry through the authenticated hourly `/api/cron/media-cleanup` job.

Before production release, review a sanitized inventory of previously deleted accounts and their remaining projects, audio, references and storage objects. New uploads register their owner before PUT; legacy generation/audio outputs are backfilled on account deletion. A legacy URL embedded in a project or character does not establish ownership of an unregistered object, so the application must not guess and delete another creator's object. An operator must reconcile that legacy inventory against trusted storage/upload evidence and approve any backfill or deletion separately.

Previous `/img` responses used a one-year immutable cache policy. A code deployment cannot revoke copies already cached by a CDN or a browser. Purge existing affected CDN cache entries at release and for historical takedowns, including configured public R2/CDN aliases; confirm new responses use `private, no-store` and that `R2_PUBLIC_URL` points through the revocation-aware `/img` proxy. Copies already downloaded by recipients cannot be recalled. Previously exposed signed/direct object URLs stop working only when the corresponding R2 object is deleted or the signature expires.

Verify `CRON_SECRET` is configured, the cleanup cron is enabled, queue failures are monitored, and the pending object count drains. A storage outage must leave revocation active with a retryable queue. Test the migration, deletion rollback, slow-upload race, stale JWT rejection, and shared project writes against a disposable database before approval. No production migration, cache purge, account deletion or storage deletion is authorized by the development work alone.
