# Wallet accounting release prerequisite

Migration 0015 preserves every existing balance and ledger row and marks existing wallets as accounting version 0. New wallets start at version 1. Version 0 wallets can spend their existing balance. Paid allowance resets refuse to interpret the legacy `bonusCredits` counter and return the internal status `wallet_accounting_review_required`; payment webhooks remain retryable.

The old counter may include consumed or refunded packs. Neither the counter nor `min(balance, bonusCredits)` proves a genuine remaining purchased balance. Do not automatically mark existing wallets as version 1, copy the old counter, replay historical payments, or alter migration 0014.

Before release, an operator must independently reconcile each affected live-owner wallet against its purchase, consumption, refund and dispute evidence. Preserve the actual total balance and lifetime spend. Review only the purchased portion still represented within that balance, and approve an exact opening snapshot. Explicit deleted-owner wallets are excluded, retain their balances and account/financial fences, and never receive an opening UPDATE. A missing owner is not an assumed live or deleted owner. The development work does not authorize executing reconciliation or applying migrations to production.

`scripts/plan-wallet-opening-balances.mjs` accepts exactly three arguments: a sanitized wallet snapshot, independent approved reviews, and a new, unused output path. It writes a dry-run JSON plan only; it has no database, credentials, network or execution mode. Exclusive output creation prevents overwriting existing files, including symbolic or hard links to evidence inputs. `releaseBlocked: false` describes the supplied evidence only: it does not prove the inventory is complete or authorize production execution.

Every snapshot row requires `userId`, `balance`, `bonusCredits`, `lifetimeSpent`, `walletAccountingVersion`, `updatedAt` and `ownerState`. Capture wallet and joined user evidence in one read-only snapshot. Use `ownerState: "live"` only when the joined user exists and its `loginMethod` is distinct from `deleted`; use `"deleted"` for an explicitly observed deleted owner. Unknown or missing owner state blocks planning, including for version-1 wallets. Deleted owners appear in `excluded`, with no SQL, regardless of any supplied approval. Already-current live wallets appear in `alreadyCurrent` and receive no UPDATE.

For either live-owner review path, require exactly one review with `userId`, `approved: true`, a named `reviewer`, `expectedBalance`, `expectedBonusCredits`, `expectedLifetimeSpent`, `expectedUpdatedAt`, `purchasedRemaining` and `evidenceTransactionIds`. All expected wallet values must match the captured snapshot exactly. `purchasedRemaining` cannot be negative or exceed the nonnegative balance. The timestamp must be an exact valid UTC string ending in `Z`, with up to six fractional digits; preserve database microseconds when exporting it, rather than round-tripping through a JavaScript `Date`. Missing, duplicate, ambiguous or stale reviews block the plan.

The ordinary transaction path requires a nonempty, unique list of positive transaction IDs. The generated statement checks that every cited immutable transaction still belongs to that wallet. A supplied ledger count cannot contradict the cited evidence. This path never treats a missing ledger as approval and never accepts an empty evidence list.

The alternate path supports only an independently reviewed **zero remaining purchased** decision for a wallet with no ledger. Missing ledger is not proof that an account was unpaid: historical partial writes, external payments and other provenance still require independent review. This path must remain blocked while the relevant independent evidence is unavailable. It requires all of the following:

- The snapshot has `ledgerRowCount: 0`, a nonempty `ledgerEvidenceId`, and an exact UTC `ledgerVerifiedAt`. Count **all** credit transactions for the wallet, without restricting type or date. Capture the count, joined owner and wallet values together; identify the sanitized capture by its evidence ID. The ledger observation cannot predate the wallet's captured update timestamp.
- The review has `purchasedRemaining: 0` and `evidenceTransactionIds: []`; do not fabricate transaction IDs or use this path for a positive or unknown purchased remainder.
- The review contains `absenceEvidence` with `kind: "reviewed-zero-purchased-without-ledger"`, `ledgerRowCount: 0`, and exactly matching `ledgerEvidenceId` and `ledgerVerifiedAt`.
- That evidence also has `zeroRemainingPurchasedApproved: true`, a nonempty written `rationale`, and nonempty unique `independentEvidenceRefs`. At least one reference must identify supporting review/provenance beyond the zero-ledger capture itself. These are independently checked references, not automatic proof merely because strings were supplied. Keep credentials, payment secrets and unnecessary account identities out of the sanitized artifacts.

The planner emits no approval from wallet values, the old bonus counter, a zero transaction count or an empty evidence list. No real reviews are created by its tests. The tests use fictional snapshots and approvals only; run them with `node --test scripts/plan-wallet-opening-balances.test.mjs`.

Every planned statement locks and requires a currently live owner and guards the original accounting version, balance, bonus counter, lifetime spend and exact update timestamp. The absence path additionally requires `NOT EXISTS` any current ledger row, so even a new transaction that leaves the wallet snapshot unchanged invalidates that plan. Planned statements change only `bonusCredits` and `walletAccountingVersion`; they do not change balance, lifetime spend or immutable ledger rows. A separately authorized operator must execute an approved complete plan in one transaction, assert **exactly one changed row per approved live wallet**, and roll back the entire transaction if any guard fails. Refresh evidence and obtain renewed review rather than loosening a failed guard. Migration 0016's active-owner triggers intentionally reject deleted-wallet mutations; do not disable those fences.

Keep legacy wallet-affecting writes quiescent throughout the approved cutover, including generation debits, purchases, refunds, grants, allowance resets and background writers. Preserve payment events for retry instead of dropping them. Rehearse the migration/data plan in isolation, refresh the exact production snapshot, apply the separately reviewed migrations and opening/period plan, then activate compatible accounting code before resuming writes. Old code must not spend or reset newly version-1 wallets. Compare balance/lifetime totals, immutable history and deleted-owner rows before and after, and retain the reviewed plan and exclusions. Do not restore old financial data or remove migration 0014's ledger/fences as a rollback shortcut.

Verified prepaid subscriptions now retain a paid service period and grant the current monthly allowance once on wallet access. Dormant elapsed months do not accumulate. Monthly boundaries are anchored to the paid period start in UTC. Only an active current subscription matching the verified invoice period qualifies. Old pre-migration annual receipts do not create inferred paid-period rows; review/reconcile those receipts separately before release. External billing schedules must be checked for duplicate responsibility.

For annual invoices paid before migration 0015, an independent operator must also approve a service-period import. Retrieve the current paid Stripe invoice and its non-prorated subscription line; match its user, subscription, item, price and exact service interval to the saved current subscription and original immutable invoice-allocation ledger/receipt. Confirm the original monthly credit quantity. Record the last month whose allowance was actually granted; do not infer that elapsed months were granted or award missed months as a lump sum. Produce an explicit per-invoice `subscriptionCreditPeriods` insert plan with those verified values and the approved cursor, guarded by the invoice unique key and current saved interval. Review wallet and period plans together before a separate, authorized transaction with row-count assertions. Missing evidence, mismatched service periods, or competing external allocation jobs block release. Do not bypass the invoice receipt by replaying a historical payment or allocation function.
